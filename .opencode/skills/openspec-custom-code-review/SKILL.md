# OpenSpec Custom Code Review

> 自定义 skill：`openspec-custom-` 前缀表示它不是 OpenSpec 官方生成的受管文件，
> 因此 `openspec update` 不会碰它。

一个 change 的 apply 完成之后、archive 之前跑。三透镜并行找缺陷，分诊成一份清单，
能自动修的修掉（先补失败测试），修不掉的交回给人。自动修分两档：直接修，或修完必须
同步改 design；拍板判据见第 3 节的两问矩阵。

产物固定写到 `openspec/changes/<change>/review.md`，随 change 一起归档。

## 输入

| 参数 | 默认 |
|---|---|
| change 名 | 从对话或 `openspec list` 推断，唯一时直接用 |
| 固定点 | 自动挑（见第 0 节）；用户给了 commit/branch 就审 `git diff <point>...HEAD` |

## 0. 先定范围，再开工

1. `openspec status --change <name> --json`，确认所有 artifact 完成。
   再读 `tasks.md`：**除 review 收口任务之外**的复选框必须全部已勾。
   review 收口任务（模板里的 `## Review 收口` 组，通常是最后一个复选框）由本次 review
   结束时才勾，它**不在**入口条件里——否则"全勾才 review"和"review 完才勾"就成死循环了。
   实现任务没勾完就不要 review，先回去 apply。
2. 定固定点。**不要用"工作区为空就失败"当判据**——仓库约定是每次修改立即 commit，实现跑完时
   工作区通常就是干净的，那样等于把正常情况判成失败。按顺序试：
   1. `git status --porcelain` 非空 → 固定点 = 工作区，看 `git diff` 加上未跟踪文件；
   2. 工作区干净 → 以**规划提交**为基线，审它之后的所有实现提交：
      `BASE=$(git log --reverse --format=%H -- "openspec/changes/<name>" | head -1)`，
      然后 `git diff $BASE`（这条覆盖逐切片提交的实现，不受"已 commit"影响）；
   3. 上面拿到空 diff（规划与实现在同一个提交里）→ 退到
      `git diff $(git rev-list --max-parents=0 HEAD)`；
   4. 四种都空，才报"没有可审的改动"并停。
   用户给了 commit/branch 时优先用他给的。**把最终采用的固定点写进 `review.md` 的「验证记录」**，
   复跑时沿用同一个，别每轮漂。
3. **接手 apply 留下的 `[RED→绿]` 标注**。`tasks.md` 里每一条 `[RED→绿: …]` 都是一张欠条：
   当初那条测试第一次跑就绿了，红证没做。本次 review 必须逐条补：

   - 删掉被钉住的那段实现 → 对应断言**必须变红** → 恢复并确认全绿；
   - 删了也不红 = 断言没有区分力 → 记一条 `medium` / `verification` finding，别放过；
   - 结果写进 review.md 的「验证记录」，一行一次：`- 红证 [3.1]：删 <什么> → <哪条断言> 变红`。

   门禁脚本会数：**任务行（复选框行）上**的 `[RED→绿]` 条数 **大于** 验证记录里的红证行数时直接阻塞，
   并把被判为欠条的行原样列出来。散文里提到这套机制（例如解释"本切片是真红，红灯异常处理不适用"）
   不算欠条——那条规矩存在的目的是让人去做红证，不是让人闭嘴。

    **抽验自证。** 自 v6 起 apply 阶段应当已对每对切片做过"删掉刚写的实现 → 该测试必须变红"的自证。
    review 至少抽验 1 对（挑最难的那对：新分支、新错误路径），删了不红就是这条断言没有区分力，
    记一条 `medium` / `verification`；`tasks.md` 里完全找不到自证痕迹的，也同样记一条。
4. 确认固定点能解析（`git rev-parse <point>`）、diff 非空。ref 错要在这里就失败，
   不要留到子代理里才发现。
5. 记下 diff 命令和提交列表，后面每个透镜都要用。

## 1. 三透镜：先探能力，再决定并行还是串行

**先探一次能力**：起一个子代理，让它跑 `git rev-parse HEAD` 并把输出贴回来。

- **能跑命令** → 走下面的并行流程。
- **不能跑**（无 tty / 沙箱 / 只读代理）→ **不要假装并行**，改由主代理**串行跑三遍**：
  每遍只带一个透镜的判据（A 一遍、B 一遍、C 一遍），中间不交叉；
  diff 由主代理先取好、直接贴进输入（对方跑不了 git，这步不能省）；
  三份结论分开记，`review.md` 的「验证记录」写明 `串行降级（子代理无命令执行能力）`。
  为什么必须串行：三个静态推演的子代理看到的是同一批文件、同一套上下文，并行只剩形式；
  串行至少保证每个轴只用自己的判据，不被别的轴污染。

并行时的规则：

三个子代理**同时**发起、前台等待。每个透镜只看自己的轴，
不要替别的透镜下判断，也不要给跨轴的优先级。

透镜 prompt 里只给路径和命令，不要把 diff 正文塞进去——让子代理自己读。
（串行降级时相反：diff 由主代理喂进去。）

### 透镜 A：spec（实现是否符合契约）

给子代理：change 的 `specs/**/*.md` 路径 + diff 命令。要求：

- 逐个场景核对：`WHEN/THEN` 在代码里是否真的成立。
- 报三类：(a) spec 要求但缺失或只做了一半；(b) diff 里有、spec 没要求（范围蔓延）；
  (c) 看起来实现了但实现是错的。
- 每条结论引用 spec 里的原文行。
- 没有 `specs/`（`skip_specs: true`）时跳过本透镜并记录。

### 透镜 B：verification（改动是否被真测试钉住）

给子代理：diff 命令 + `seams.md` + 测试目录路径。
判定标准全文见 `references/verification-lens.md`，核心一句：

> 对每个改动面，说出最小的真实回归，然后问：**这个回归会让某条断言失败吗？**

不会 → 记一条 gap。同时检查测试质量：同义反复、断言源码文本、只测不抛错、
mock 调用次数、端到端透传但没检查改动结果。

### 透镜 C：standards（是否符合仓库标准）

给子代理：diff 命令 + 仓库里记录编码规范的文件（`CONTRIBUTING.md`、
`docs/` 下的规范、`.editorconfig` 之外的约定）+ `references/standards-baseline.md`。
规则：**仓库文档化的标准永远优先**；baseline 里的 smell 一律是判断而非硬违规；
工具已经强制的（lint、格式、类型）跳过。

### 失败处理与取证降级

任一透镜失败、超时或返回空：记下它的名字，用剩下的继续，
**最后必须报告"本次 review 不完整"**，不能说成干净通过。

子代理可能根本没有命令执行能力（无 tty、沙箱、只读代理）。它必须如实回报
"无法执行 `git diff` / 测试命令"，此时按取证降级处理：

- 静态推演可以继续（读 `.git/logs/HEAD`、读文件、读测试），但结论只能算"待验证"；
- **红证 / 变异验证 / 跑测试由主代理补跑**，子代理不得声称"已验证"；
- `review.md` 的「验证记录」必须写明 `取证降级：静态推演`，并列出主代理补跑了哪几条；
- 有 high/medium 结论缺实测支撑、主代理也补不了 → 降级成 `decision_needed`，
  不要以"静态看应该没问题"结案。

## 2. Triage

等三个透镜全部回来再开始，边收边判会漏。

1. **归一化**：每条 finding 编 `R1`、`R2`…，带 `source`（哪个透镜）、`title`、
   `detail`、`location`。**此时不要合并去重**，会把线索弄丢。
2. **验真**：这条声称的行为真的能发生吗？顺着调用方、上游守卫读，
   尽量给出确定的能 / 不能。给不出证据的，判 `maybe-false`。
   不要因为"和刚否掉的 R3 很像"就否掉 R5——除非两者指向同一处同一行为。
3. **定级**：只看单次发生的后果，不看多稀有、不看好不好修。
   - `high`：数据丢失/损坏、安全暴露、静默算错、无绕法的路径断裂
   - `medium`：坏了但会被发现并能绕过，或影响面有限
   - `low`：外观问题、轻微不便
   - `false`：不成立（附上什么推翻了它）
   - `maybe-false`：证据不足（附上什么能定案）
4. **去重**：按**根因**分组，不按文件位置。同位置可能是两个不同的 bug。
   每组取最高的 verdict，记住成员的 `R` 编号和来源。
5. **拒绝**：`false` 一律拒；`low` 且修复成本大于收益的拒。
6. **跨透镜冲突，以 spec 为准**：spec 轴说"删掉未承诺行为的断言"，verification 轴说
   "这里没有钉子"，是同一处代码在契约空白区给出的相反处方。裁决规则：
   **回归 = 承诺过的行为被破坏**，没承诺过的行为不算 gap。把它记成 `contract-gap`，
   路由 `decision_needed`（"要钉住它得先写 requirement"），**不要折中成一条 low 了事**。

## 3. Route

每条去重后的 finding 归入三类之一：

| 路由 | 判据 |
|---|---|
| `patch` | 修法无歧义、不新增公共接口、不靠猜测的状态 |
| `decision_needed` | 需要用户意图才能修对。列出选项各一行 + 推荐哪个及理由 |
| `defer` | 不是本次改动引入的问题 |

判据里的"无歧义"要严格：拿不准就 `decision_needed`，**不许猜着改**。

### 能不能自动做，不看严重度，看两件事

`patch` 只说明修法清楚，不代表可以自己拍板。再问两个问题：

```
                      修复会让 design 里已写下的选择失效吗？
                               否                     是
                  +----------------------+----------------------+
   回滚成本低     |  直接修，记一笔即可  |  自动修 + 必须同步   |
                  |                      |  改 design 对应段落  |
                  +----------------------+----------------------+
   回滚成本高     |  问                  |  问                  |
                  +----------------------+----------------------+
```

- **回滚成本**：改的是可观察契约、数据结构、公共接口、已归档产物，或需要数据/迁移动作 → 高；
  一句话改回去就能复原 → 低。
- **"是"这一格的硬边界**：`specs/`、`proposal.md`、`seams.md` 的契约段落**永远不许**自动改。
  修复若要改 spec 承诺的行为，一律 `decision_needed`。矩阵里说"同步改 design"，改的是 design
  自己的决策 / 风险 / Non-Goals——它是实现文档，不是契约。
- **默认值：低优先级 + 有歧义时，默认"记录限制"而不是"改行为"。** 两个方向都说得通时，
  选把限制写进 design 的 Non-Goals 或扩写 `seams.md` 的盲区：零行为漂移、可逆、诚实。
  改代码能让测试变绿，却会把契约里的洞永久藏起来。

### 自动决策的三条护栏

1. **必须有证据**：一条会红的测试、一次变异验证、或一段命令输出。给不出证据的，只能记成
   note，不能记成 `fixed`。
2. **每轮最多 3 条**。超过 3 条通常不是发现多，而是 design 没定清楚——停下来问一次。
3. **单独成区**：所有自动决策在 `review.md` 的 `## Auto-decided` 里写清"选了什么、为什么、
   怎么撤销"，归档前扫一眼就能覆盖，不用重读全部 findings。

## 4. Fix（只修 `patch`）

每条 `patch` 必须按红绿走，修复本身也是 TDD：

1. 先写一条能复现该缺陷的测试，运行，确认它失败（红）。这条测试就是回归证据。
2. 再做最小修复，运行，确认变绿，且原有测试仍全绿。
3. 在 `review.md` 里把该条标成 `fixed`，附上测试名和命令。

缺验证类（行为本来是对的，只是没钉子）例外：补的测试会直接绿，改用**红证**——故意把实现
改坏一次，确认新断言变红，再改回。红证与红绿一样算证据。

修复不得改动 `specs/`、`proposal.md`、`seams.md` 的意图段落。
真要改契约，那是 `decision_needed`，交回给人。

## 5. 复跑与收口

修完重跑三透镜，**只审这一轮的修复**。最多两轮。

结束后：

| 状态 | 条件 | 能 archive 吗 |
|---|---|---|
| ✅ 通过 | open 的 high/medium/low 全为 0，无失败透镜 | 能 |
| ⚠️ 有条件通过 | open 的 high 0 / medium 0，只剩 low open、`defer`、已拒绝项 | 能 |
| ⛔ 阻塞 | 还有 open 的 high/medium，或任一透镜失败/未完成 | **不能** |

两条判据不再重叠：区别就是"有没有 open 的 low"，前者零 open，后者允许 low 留着。

**收口前必须跑门禁脚本**（CLI 只数复选框、不读 verdict，这一步是唯一能把它变成可执行判据的环节）：

```bash
node scripts/check-review.mjs openspec/changes/<change>/review.md
```

它**不读叙述，只读结构**：

- Verdict 行的 `high N` / `medium N` 必须是 **0**；括号里写"均已 fixed"**不构成豁免**
  （v1 就是因为信这句话，被 `medium 2（已降级为 low，留待后续）` 一句话放行）；
- 它再从每个 `### F<n> [severity]` 块的 `- 状态：` 反推还有哪些 open（状态以
  `fixed` / `rejected` / `closed` 开头才算关闭；**缺 `- 状态：` 一律算 open**）；
- 两边对不上就阻塞。想蒙过去得同时改两处结构化字段，而不是换一种说法。

退出码：`0` 可收口；`1` 阻塞（⛔ / 有 open 的 high/medium / Verdict 与 Findings 不一致 /
`[RED→绿]` 欠条没还）；`2` 结构或文件问题（缺 Verdict、缺 `high N` 计数、`## 验证记录` 写了不止一节、文件读不到）。
脚本不在仓库里时先补 `scripts/check-review.mjs`（模板里有这份）。

**跑对副本、跑对目录。**（当前判据版本 `gate v7`） 每个仓库自带一份 `scripts/check-review.mjs`，副本会落后于模板；
在别的目录下执行会拿到那份旧脚本，它的 `0` 是**旧判据的 0**。所以：在**被审查仓库的根目录**跑它自己的副本，
并看成功行末尾的判据版本（`✓ review 可收口（gate v5）`）——版本比仓库 schema 落后，就先把脚本同步过来再判。

**写"无发现"要付举证。** Verdict 是 ✅ 且 Findings 为空时，验证记录里必须逐透镜写出**实际做过的动作**：
跑了哪条命令、读了哪个文件的哪一节、做了几次红证或变异。写不出可复述的动作，就不许写"无发现"——
那说明这次只是通读，不是审查。`无发现` + 空验证记录 = 最容易被当成"干净"的假绿。

## 6. 写 `review.md`

```markdown
# Review: <change>

## Verdict
<通过 / 有条件通过 / 阻塞> — high N / medium N / low N / auto-decided N / rejected N
透镜：spec ok / verification ok / standards 失败（原因）

<!-- N = 仍未处理的条数；已修复的写进括号，例如 medium 2（均已 fixed）。
     scripts/check-review.mjs 按这个约定解析：破折号前是状态词，分号前是计数。 -->


## Findings

### F1 [high] <一行标题>
- 来源：spec + verification
- 位置：`file:line`
- 证据：<能发生，以及会发生什么>
- 路由：patch
- 状态：fixed（回归测试 `test/xxx.test.mjs` "..."）

### F2 [medium] <标题>
- 路由：decision_needed
- 状态：open
- 选项：A ...（推荐）／B ...

## Auto-decided
- A1 [F4] 选了什么 —— 为什么（证据：测试 / 变异 / 命令输出）—— 怎么撤销（改哪个文件、删哪条测试）

## 已拒绝
- R3 [false] <标题> — 推翻依据：<...>

## 验证记录

- 固定点：`<BASE 或 分支>`，`git diff <BASE>` 覆盖 N 个提交（为什么选它：工作区干净 → 取规划提交）
- 测试：`<seams.md 里的命令>` → x pass / y fail
- 取证：三透镜均可执行命令 / `取证降级：静态推演`（主代理补跑了：…）
- 红证 [3.1]：删 `<哪段实现>` → `<哪条断言>` 变红，已恢复（`[RED→绿]` 几条就写几行，门禁会数）
```

## 什么不算缺陷

- 编译器 / 类型检查器 / lint 已经保证的
- 本次没碰的代码的既有问题（可以提，但归 `defer`）
- 单纯的"覆盖率低"、"没有测试文件"
- 风格偏好，且仓库没有文档化这条规范
- 没有证据支撑的"这里可能会出问题"

## 反模式

- 把三个透镜的结论揉成一份排序清单 —— 两个轴会互相遮蔽。
- 为了显得有产出而硬凑 low 级 finding。
- 修 `decision_needed` 的项 —— 那是在替用户做决定。
- 拿 `low` 当"可以自动改行为"的许可证 —— low 只说明影响小，不说明歧义小。
- 为了省一次提问，把该问的塞进 `## Auto-decided` —— 决策会伪装成修复，且没人再审。
- 修复不带回归测试 —— 下次重构会再漏一遍。
- 复跑超过两轮 —— 说明问题需要人来看。
