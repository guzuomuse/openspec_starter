# TDD guide

> 这份文件是 `tdd-flow` schema 的判定标准，供 propose 与 apply 时查阅。
> 它改写自通用的 TDD skill，并按 OpenSpec 的产物做了裁剪：接缝写进 `seams.md`，
> 切片写进 `tasks.md`，循环规则写在 schema 的 `apply.instruction` 里。

## 循环

红 → 绿。一个切片 = 一条失败测试 + 一份最小实现。循环里只做这两件事。

- **先红后绿**：没有看到失败的测试，不算开始实现。
- **绿了当场自证**：GREEN 之后删掉刚写的那段实现，重跑测试，必须看到这条测试变红，再恢复。
  仍然绿说明让它变绿的是别处的代码，你亲手写的这段没有被任何断言钉住——那是"钉子归属"问题，
  不是小事：红灯只证明断言当时有区分力，不证明变绿的是刚写的那段。
- **先提交再自证**：恢复手段是"回到提交里的实现"，所以 GREEN 必须先落进提交（或先备份副本）。
  用 `git checkout` 恢复**未提交**的实现等于把它换成上一个提交的空壳，随后的"复跑绿"是假绿。
- **一次一个切片**：不预写后面切片的测试，也不预写后面切片的功能。
- **重构不属于循环**：它是 review 阶段的事。
- **红灯意外通过**：测试第一次跑就绿，说明功能已存在或断言是空转。停下来报告，
  不要删断言让流程继续。

## 红的两步

第一次红往往不是断言红，别把它当成验收通过：

1. 先写测试，跑一次。失败是 `ERR_MODULE_NOT_FOUND` 这类"符号还不存在"——合法，
   它证明测试真的在调一个不存在的东西。
2. 补一个空壳（导出函数，返回 `undefined`），再跑一次。这次必须是断言失败，
   而且你能一眼看出"期望 5400、实际 undefined"。

空壳之后测试就绿了，说明断言什么也没验证（见上面的"红灯意外通过"）。

测试命令只写一次，放在 `seams.md` 对应接缝那一行；任务里引用接缝编号，不重复命令。

## 好测试

测试验证行为，透过公共接口。实现可以整体重写，测试不该跟着改。

- 读起来像一条规格："用户可以用有效购物车结账"。
- 只调公共 API，不碰私有方法、内部状态。
- 名字描述 WHAT，不描述 HOW。
- 一条逻辑断言。
- 期望值是独立的已知值（字面量、手算样例、规格里的例子），不能按实现的算法重算。

重写实现后测试仍然通过，才说明它测的是行为。

## 接缝（seam）

接缝是你在测试里调用的那个公共边界。**测试只写在接缝上。**

- 接缝要先确认，再写测试。确认记录进 `seams.md`，包括它的盲区。
- 接缝要少而准：关键路径和复杂逻辑，不追求覆盖率。
- 接口形状还没定，先解决形状（design 或 design skill），不要先写测试。
- 需要新接缝时停下来问，确认后补进 `seams.md`。

## 三个反模式

- **实现耦合**：mock 内部协作者、测私有方法、绕过接口去查数据库。特征是
  "重构后测试红了，但行为没变"。
- **同义反复**：断言把实现算法抄了一遍（`expect(add(a,b)).toBe(a+b)`），
  构造上永远通过，永远不会和代码意见相左。
- **横向切片**：先把所有测试写完，再一次性写实现。这时测的是**想象中**的行为，
  测试对真实变化不敏感，还提前锁死了测试结构。永远用垂直切片：
  一个测试 → 一个实现 → 下一个测试。

## Mock 边界

只在系统边界 mock：外部 API、数据库（优先用测试库）、时间与随机、文件系统（视情况）。

不要 mock 你自己的类、模块、内部协作者——任何你控制的东西。

边界要设计得可 mock：依赖注入（传进来，而不是内部 new），SDK 式细粒度接口
（每个操作一个函数，而不是一个通用 fetch 加分支）。

## 与 OpenSpec 产物的对应

| 产物 | 放什么 | 不放什么 |
|---|---|---|
| `specs/` | 可观察的行为、输入输出、错误条件 | 类名、函数名、库选择 |
| `seams.md` | 接缝、覆盖的行为、测试命令、盲区 | 具体用例清单 |
| `tasks.md` | 成对的 RED/GREEN 切片 | 重构、模糊的"加测试" |
| `apply` 阶段 | 一个切片一对勾 | 批量写测试、批量写实现 |
