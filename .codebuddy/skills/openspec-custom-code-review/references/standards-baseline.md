# Standards baseline（透镜 C 的判断基线）

三条例外先行：

1. **仓库文档化的标准永远优先。** 仓库明确认可的做法，baseline 不许再标。
2. **永远是判断，不是硬违规。** 写"possible Feature Envy"，不写"违反规则"。
3. **工具已经强制的跳过。** lint、格式化、类型检查管的事不用人再说一遍。

## 可疑的坏味道

每条读作：是什么 → 怎么修。只匹配本次 diff 里出现的。

- **神秘命名**：函数/变量/类型名看不出它做什么、存什么。→ 改名；想不出诚实的名字，说明设计本身糊。
- **重复代码**：同一个逻辑形状出现在多个 hunk 或文件里。→ 抽出来，两处都调它。
- **依恋情结**：一个方法伸手去掏别的对象的数据，比自己家的还多。→ 把方法搬到它羡慕的数据那里。
- **数据泥团**：几个字段或参数总是结伴出现。→ 打成一个类型，传那个类型。
- **基本类型偏执**：用字符串或原始值代表一个本该有自己类型的领域概念。→ 给这个概念一个小类型。
- **重复的 switch**：同一个类型上的 switch / if 级联在 diff 里出现多次。→ 换成多态，或共用一张映射表。
- **霰弹式修改**：一处逻辑改动迫使 diff 里到处都要改。→ 把总是一起变的东西收到一个模块。
- **发散式变化**：一个文件因为几个不相干的原因被改。→ 拆开，让每个模块只因一个原因变。
- **夸夸其谈的通用性**：为 spec 里没有的需求加了抽象、参数、钩子。→ 删掉，内联回去，等真需要。
- **消息链**：`a.b().c().d()` 这种调用方不该依赖的长导航。→ 在第一个对象上藏成一个方法。
- **中间人**：主要工作就是往下转发的类或函数。→ 砍掉，直接调真正的目标。
- **被拒绝的遗赠**：子类或实现者忽略了继承来的大部分东西。→ 别继承，改组合。

## 报告口径

- 引用仓库规范时给出**文件 + 那一条规则**。
- 引用 baseline 时给出**名字 + 引用的 hunk**。
- 文档化的标准可以算硬违规；baseline 一律是判断。
- 每条 finding 都要说清"它会在哪里造成麻烦"：哪个调用方会分叉、哪条规则会破、
  读代码的人会怎么误解。说不出具体的麻烦，降级或丢掉。
