# Verification lens（透镜 B 的判定标准）

问题只有一个：**改动带来的回归，有没有一条会变红的断言钉住它？**

## 证据规则

- 说一条测试覆盖或漏掉什么之前，先打开它读。
- 说"没有测试"之前，先按符号名和 import 搜全仓库。按预期路径猜不算。
- 说清你搜了什么、看到哪一步。撑不住的结论直接丢掉。
- 不要给严重度、置信度、优先级——那是 triage 的事。

## 六步

### 1. 筛

逐个改动面看，跳过不改变行为的：格式化、注释、重命名、纯类型改动、
原样透传的 getter。跳过之后就别再看它的调用方和测试。

也跳过不值得测的：静态文本（prompt、文档）、LLM 输出、
构建/依赖/配置这类由 CI 自己验证的。

**不要跳过测试本身的改动**：被删掉或弱化的测试，在第 4、5 步查。

全被跳过就报干净。

### 2. 命名改动后的行为

对每个留下的改动面，说清和之前哪里不同：输出、副作用、分支、错误路径、
schema 或事件形状、默认值、校验规则、对外契约。一个行为一条。

### 3. 找到观察者

把每个改动过的行为追到真正观察它的代码：直接调用方、注册入口（路由、命令、DI）、
契约消费方（schema、事件、API、读库的地方）。

1~3 跳通常够。遇到"测试能接住""消费方看不到这个变化""下一跳只能猜"就停。

### 4. 说出回归，然后查测试

对每个消费方，说出它能看到的最小真实回归：分支反了、默认值丢了、字段漏了、
旧错误码回来了、集成调用被跳过。

> "这行删掉也没有测试会红"不是回归。

没有回归（状态不可达、防御性分支、别处已经保证了）→ 丢掉这条路径，不算 finding。

然后读相关测试，问：**这个回归会让某条断言失败吗？**

- 会 → 已验证，无 finding。
- 没有测试跑这条路径，或测试被跳过、不稳定、平时不跑，或跑了但没检查改动结果
  → `regression gap` / `broken-verification gap`。

一条测试算数，必须满足：平时会跑 + 有断言观察改动的输出、分支或契约。

**不算数的情况**：对源码文本断言、只断言不抛错、只有快照、
检查 mock 调用次数或日志、手动检查、把集成 mock 掉的测试、
端到端跑过但没检查改动结果的测试、陈旧的断言或 fixture。

### 5. 查被碰过的测试

测试断言的内容不是这次改动后应有的行为 → `stale-verification gap`，
说明它应该断言什么。测试已经不再验证任何东西 → 建议删掉。

### 6. 确认

写 finding 之前，把依赖的测试和搜索结果重新打开一遍。确认：
回归真实存在，且你读过的测试确实接不住它。

## 不要报

- 编译器或类型检查器保证的
- 集成/契约/端到端测试已经验证过的
- 单纯的覆盖率低、没有测试文件
- 本次没碰的代码

追踪过程中顺手发现的缺陷，另起一节 `其他发现`，不要专门去找。

## 输出格式

每个 gap 一个块，必须能独立站住（triage 不会再验一遍 gap）：

```markdown
### <一行标题，点出缺的是什么验证>

- **改动的面**：<行为或契约>，`file:line`
- **受影响的消费方**：具体到名字和 `file:line`，不要写"该函数的调用方"
- **现有测试证据**：相关测试断言了什么 `file:line`；或你搜了什么、结果如何
- **缺的验证**：应该补的断言，或旧断言应该改成什么
- **演示**：回归是什么，以及你读的测试为什么不会红
- **后果**：什么会带着问题上线
- **处置**：要加或要改的测试，贴合本仓库已有的测试写法
```
